# StructLens v0.4 Structural Reliability Implementation Plan

> **Required workflow:** use Superpowers `subagent-driven-development` and
> `test-driven-development`. Each production behavior starts with a failing test,
> receives the minimum implementation, is refactored while green, then passes
> specification and quality review. Use Luna xhigh for bounded implementation,
> Terra xhigh for integration/scientific review, and Sol only for an unresolved
> architecture or scientific-semantics escalation.

**Goal:** deliver a locally installed StructLens v0.4.0 that completes the v0.3
GUI workflow and adds auditable coordinate QC, blind pocket detection, free-volume
measurement, mutation-aware pocket comparison, canonical reports, exports, CLI,
PyMOL visualization data, and an English manual.

**Architecture:** pure immutable scientific contracts in `core`, orchestration in
`application`, validated external adapters in `integrations`, and consumer-only
presenters/controllers in `plugin/gui`. One canonical `AnalysisReport` feeds every
output surface. No scientific rules or arbitrary JSON payload assembly live in Qt.

**Stack:** Python 3.11+, NumPy, SciPy, Biopython, FreeSASA, openpyxl, Qt5/Qt6,
pytest/pytest-cov, Hypothesis, Ruff, mypy, PyInstaller, Inno Setup, GitHub Actions.

**Primary design:**
`docs/superpowers/specs/2026-08-30-v0.4-structural-reliability-design.md`

## Global rules

- Work only in branch `codex/structlens-structural-reliability` at worktree
  `.worktrees/structural-reliability`.
- Do not modify or publish from `main`.
- Preserve compatibility with v0.3 projects, bundle readers, and CLI invocation.
- Do not push, tag, or create a GitHub release before explicit user approval after
  local testing.
- Before every commit run the focused tests, then `ruff check`, relevant mypy, and
  inspect `git diff --check` plus `git diff`.
- Before task/phase completion use a Luna implementation pass, a specification
  review, and a Terra integration/scientific review. Address all critical/high
  issues.
- New scientific modules require at least 90% branch coverage. The final repository
  gate is at least 80% branch coverage measured honestly, including runnable GUI
  code.
- Use immutable frozen/slot dataclasses or tuples for scientific values. GUI state
  changes create replacements rather than mutating report data.
- All user/file input is boundary-validated. Never use `eval`, pickle, imported
  scripts, or unbounded allocations.
